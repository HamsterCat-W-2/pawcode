# v0.5.4 Skills 与自定义命令 MVP 技术设计

## 1. 目标

v0.5.4 为 PawCode 增加轻量、可审查的 Skills 与自定义命令能力。用户可以把重复的项目工作流、代码规范和工具限制写成 Markdown 文件，并在需要时显式加载。

Skill 的定位是“受控的上下文模板”，不是新的执行引擎：

```text
用户执行 /skill <name>
        ↓
SkillRegistry 发现并校验 Markdown Skill
        ↓
将 Skill 指令和允许工具集应用到当前 Runtime
        ↓
AgentRuntime → ToolRegistry → PermissionManager → Tool
```

Skill 不直接调用文件、命令、MCP 或网络能力；所有实际副作用仍由既有 `ToolRegistry` 和 `PermissionManager` 控制。

## 2. 范围

### 2.1 本期实现

- 用户级和项目级 Skill 发现；
- Markdown + YAML frontmatter 的 Skill 定义；
- `/skills` 列出当前可用 Skill；
- `/skill <name>` 显式激活一个 Skill；
- `/skill` 显示当前激活 Skill 与用法；
- Skill 内容按需注入 system prompt；
- Skill 声明的 `allowedTools` 限制当前 Runtime 可用工具；
- 同名 Skill 的固定优先级和可见来源；
- Skill 文件大小、名称和 frontmatter 的安全校验；
- 对激活、未知 Skill、无效 Skill 和工具限制的自动测试。

### 2.2 本期不实现

- Skill 内嵌 Shell、JavaScript、Python 或其他可执行脚本；
- 从网络下载或自动安装 Skill；
- Skill 自动根据模型意图隐式激活；
- 多个 Skill 叠加、依赖、继承或工作流编排；
- Skill 级模型切换、独立 MCP Server 启动或独立权限策略；
- Skill 修改全局、项目或本地配置；
- 跨 Session 持久化“当前激活 Skill”；
- HTTP MCP transport。

## 3. 目录和优先级

### 3.1 发现目录

```text
~/.pawcode/skills/<name>.md              用户级
<workspace>/.pawcode/skills/<name>.md    项目级
```

只扫描上述目录第一层的 `.md` 文件：

- 不递归扫描子目录；
- 不跟随符号链接到发现目录之外；
- 忽略隐藏文件、非普通文件和超过大小限制的文件；
- 缺少目录不是错误，等同于没有对应范围的 Skill。

限制为固定目录和非递归扫描，避免把任意仓库 Markdown 误当作可执行工作流，也避免大项目启动时扫描大量文件。

### 3.2 名称和冲突

Skill 名称由 frontmatter 的 `name` 决定，必须匹配：

```text
^[a-z0-9][a-z0-9-]{0,39}$
```

同名 Skill 使用固定优先级：

```text
项目级 > 用户级
```

项目级 Skill 覆盖同名用户级 Skill，但 `/skills` 会显示来源和“已覆盖”状态。这样项目可以提供团队统一工作流，同时用户仍可保留个人通用 Skill。

同一目录中出现两个文件声明相同 `name` 时，该范围的冲突 Skill 均不加载，并输出诊断；不能按目录遍历顺序静默选择一个。

## 4. Skill 文件格式

### 4.1 示例

`<workspace>/.pawcode/skills/review.md`：

```md
---
name: review
description: 按项目规范审查当前未提交改动。
allowedTools:
  - git_diff
  - read_file
  - grep
  - list_files
---

先读取 `AGENTS.md`、相关技术文档和当前 diff。
输出按风险级别排序的问题；除非用户明确要求，不修改文件、不提交代码。
```

### 4.2 Frontmatter schema

| 字段           | 类型     | 必填 | 约束和含义                                                |
| -------------- | -------- | ---- | --------------------------------------------------------- |
| `name`         | string   | 是   | Skill 唯一标识，用于 `/skill <name>`                      |
| `description`  | string   | 是   | `/skills` 展示的简短用途，长度 1～200                     |
| `allowedTools` | string[] | 否   | 激活后允许使用的 PawCode 工具完整名称；缺失表示不额外限制 |

frontmatter 以首行 `---` 开始、下一个独占行 `---` 结束。MVP 只接受标量字符串和字符串数组，不支持 YAML 锚点、复杂对象、多文档或自定义标签。

正文必须是非空 Markdown 文本，最大 32 KiB。frontmatter 不进入 Skill 指令正文。

### 4.3 工具字段语义

`allowedTools` 是允许列表，不是授予权限：

```text
Skill allowedTools
        ∩
当前 ToolRegistry 定义
        ∩
路径规则 disabledTools
        ∩
PermissionManager 授权结果
```

因此 Skill 即使声明 `write_file` 或 `mcp_demo_echo`：

- 工具不存在时不会凭空创建；
- 路径规则禁用时仍不能执行；
- 用户拒绝授权时仍不能执行；
- MCP stdio 与未来 HTTP MCP 工具均只以工具名参与该交集，Skill 不依赖 transport 类型。

若 `allowedTools` 为空数组，表示禁止该 Skill 运行期间调用任何工具；适用于纯写作、分析或规划类 Skill。

## 5. Runtime 集成

### 5.1 激活状态

在当前交互 Runtime 中维护：

```ts
type ActiveSkill = {
  name: string
  source: 'user' | 'project'
  instructions: string
  allowedTools?: string[]
}
```

激活状态仅存在于内存：

- `/new` 创建新 Session 后不继承；
- `/resume`、`/branch` 和程序重启后不继承；
- Session 历史不写入 Skill 正文；
- 用户需要时重新执行 `/skill <name>`。

不持久化的原因是 Skill 文件可能被编辑、删除或被项目覆盖；恢复旧 Session 时自动重放旧指令会造成不可见的行为变化。

### 5.2 System prompt 合成

激活 Skill 后，后续模型请求使用：

```text
基础 system prompt
  + 项目上下文（PAWCODE.md、AGENTS.md、记忆、路径规则）
  + 当前 Skill 指令
```

Skill 指令使用明确边界包装，例如：

```text
<pawcode-skill name="review" source="project">
...
</pawcode-skill>
```

边界的作用是让模型、日志和测试能识别指令来源，避免把 Skill 正文混同于 PAWCODE.md 或用户输入。

激活 Skill 不修改 `SessionManager` 的历史消息，也不重新创建 ModelAdapter、MCP Client 或 ContextProvider。它只替换 Runtime 后续请求使用的动态 system prompt 和工具可见集合。

### 5.3 工具可见性

当前 `ToolRegistry` 支持按路径规则禁用工具。v0.5.4 新增“额外 disabled 工具”计算：

```text
全部已注册工具
  - 路径规则 disabledTools
  - (全部工具 - activeSkill.allowedTools)
```

Skill 未设置 `allowedTools` 时，沿用现有路径规则；设置后只向模型暴露允许列表中的工具。执行阶段也必须传入同一组 disabled 工具，避免模型不可见限制与实际执行限制不一致。

## 6. CLI 命令设计

### 6.1 `/skills`

```text
/skills
```

输出所有已解析 Skill：

```text
可用 Skills
- review [project]  按项目规范审查当前未提交改动
- release [user]    生成发布前检查清单
```

若项目级 Skill 覆盖用户级同名 Skill：

```text
- review [project]  按项目规范审查当前未提交改动（覆盖 user）
```

无效文件不展示为可用 Skill，但在启动或 `/skills` 输出中给出安全诊断。

### 6.2 `/skill <name>`

```text
/skill review
```

成功后：

```text
已激活 Skill：review [project]
工具限制：git_diff, read_file, grep, list_files
```

之后用户正常输入任务；当前 Skill 保持生效，直到执行 `/skill clear`、切换 Session 或退出。

### 6.3 `/skill clear` 和 `/skill`

```text
/skill
/skill clear
```

- `/skill`：显示当前激活 Skill、来源、工具限制和用法；
- `/skill clear`：清除当前 Skill，恢复基础上下文和原有工具可见性；
- 未激活 Skill 时 `/skill` 明确显示“当前未激活 Skill”。

`/skill` 不接受正文、文件路径或 Shell 参数，避免把交互命令变成任意文件加载入口。

## 7. 安全边界

1. Skill 只能从固定用户级和项目级目录读取；
2. 只读取普通 Markdown 文件，拒绝目录、符号链接逃逸和超大文件；
3. Skill 只能减少工具可见性，不能放宽 `PermissionManager`、路径规则或工作区限制；
4. Skill 不能携带 API Key、MCP env、模型凭据或命令执行配置；
5. 不自动激活 Skill，防止仓库中的文件在用户无感知下改变 Agent 行为；
6. 不执行 Skill 正文中的命令；正文只是模型指令；
7. `/skills` 和 `/skill` 的诊断不得打印完整正文或敏感文件内容；
8. JSON 模式不支持交互 `/skill`；非交互命令行 MVP 不增加 `--skill` 参数，避免未确认的自动行为。

## 8. 模块划分

```text
src/skills/
├── skill-schema.ts       frontmatter 的最小 schema 和名称校验
├── skill-loader.ts       固定目录发现、读取、安全校验、优先级和诊断
├── skill-registry.ts     可用 Skill 索引、激活状态和工具限制计算
└── skill-types.ts        Skill、来源、诊断和激活状态类型

src/cli.ts                /skills、/skill 命令解析与展示
src/runtime/              Runtime system prompt / disabled tool 集成点
tests/skills-*.test.ts    发现、覆盖、校验、激活和工具限制测试
```

`SkillRegistry` 不依赖 `McpStdioClient`、`McpHttpClient` 或任何具体 Tool 实现；它只处理 Tool 名称字符串和已注册工具集合。

## 9. 错误语义

| 场景                     | 行为                                                   |
| ------------------------ | ------------------------------------------------------ |
| 目录不存在               | 正常，返回空集合                                       |
| 文件不是普通 Markdown    | 跳过并诊断                                             |
| 文件超 32 KiB            | 跳过并诊断                                             |
| frontmatter 缺失或不合法 | 跳过并诊断                                             |
| name 不合法              | 跳过并诊断                                             |
| 同层同名冲突             | 两个冲突 Skill 均跳过并诊断                            |
| 项目级覆盖用户级         | 项目级可用，`/skills` 标注覆盖关系                     |
| `/skill` 名称不存在      | 保持当前 Skill 不变并提示可用名称                      |
| Skill 声明未知工具       | 激活时保留名称，但运行时不暴露任何不存在工具；输出警告 |
| `/skill clear`           | 清除内存状态，恢复基础 Runtime 规则                    |

## 10. 测试计划

### 10.1 Loader

- 用户级、项目级目录发现；
- 项目级覆盖用户级；
- 同层重复 name；
- 名称、description、allowedTools schema 校验；
- 空正文、超大文件、符号链接和非普通文件；
- 不存在目录与无效文件诊断。

### 10.2 Registry 和 Runtime

- 激活后 system prompt 包含明确 Skill 边界；
- 清除后 Skill 指令不再出现；
- `allowedTools` 仅向模型暴露允许工具；
- 空数组禁用全部工具；
- 路径规则和 Skill 限制取交集；
- Skill 不会改变 PermissionManager 的授权结果；
- Session 切换不继承 ActiveSkill；
- MCP 工具名称可以出现在 allowedTools，但 Registry 不依赖 transport。

### 10.3 CLI

- `/skills` 输出来源和覆盖状态；
- `/skill <name>` 激活并显示工具限制；
- `/skill` 显示当前状态；
- `/skill clear` 恢复默认状态；
- 未知名称和非法参数不改变当前状态；
- 交互命令不污染 NDJSON stdout。

## 11. 验收标准

- 用户和项目可以各自提供 Markdown Skill；
- 同名覆盖关系稳定、可见、可测试；
- Skill 只在显式 `/skill <name>` 后生效；
- Skill 指令只影响后续模型请求，不写入 Session 历史；
- Skill 只能收紧工具可见性，不能绕过权限或工作区保护；
- Skills 与 MCP stdio、未来 HTTP MCP 只通过工具名和 ToolRegistry 交互；
- 现有 CLI、会话、上下文、MCP、权限和完整测试继续通过；
- 新增和修改代码按项目约定提供高密度中文注释。

## 12. 后续演进

在 MVP 稳定后再评估：

1. 多 Skill 组合与冲突解释；
2. 非交互 `--skill <name>`；
3. Skill 专属参数模板；
4. 可追踪的脚本与辅助资源，但仍必须走 ToolRegistry 和 PermissionManager；
5. Skill 包、签名、来源和远程分发。

这些能力不能改变 v0.5.4 的核心原则：Skill 是可审查、显式激活的上下文和工具约束，不是绕过 PawCode 安全模型的自动执行机制。

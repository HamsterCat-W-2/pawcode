# v0.5.2 MCP 启动性能优化技术设计

## 1. 背景

当前 MCP Client 在 `createRuntimeBundle()` 中同步加载所有启用的 MCP Server：

```text
Server A spawn → initialize → tools/list
                         ↓
Server B spawn → initialize → tools/list
                         ↓
创建 AgentRuntime
```

因此，多个 Server 的启动时间会累加；任意一个 Server 在握手或工具发现阶段超时，也会拖住整个 Runtime 创建过程。

当前已具备的安全边界不能改变：MCP Server 仍然通过 `spawn(..., { shell: false })` 启动，工具仍然进入 `ToolRegistry` 和 `PermissionManager`，失败的 Server 不能阻断内置工具。

## 2. 目标与非目标

### 2.1 目标

- 启用多个 MCP Server 时并行执行独立的 spawn、initialize 和 tools/list 流程；
- 一个 Server 启动失败、超时或返回非法协议数据时，只隔离该 Server；
- `--verbose-startup` 可以看到 MCP 总耗时，以及每个 Server 的关键阶段耗时；
- 保持工具注册顺序稳定，避免并行完成顺序改变模型工具列表；
- Runtime 关闭时仍然回收所有成功启动的 MCP 子进程；
- 不改变现有配置格式、权限行为和 MCP 工具调用协议。

### 2.2 非目标

- 本次不实现 MCP Server 进程常驻或跨 Session 复用；
- 本次不实现工具发现缓存；
- 本次不实现动态 `tools/list_changed` 刷新；
- 本次不把 MCP Server 加载改成后台异步，因为 Agent 第一次模型请求必须拿到完整工具列表；
- 本次不调整 `timeoutMs` 的配置语义。

## 3. 设计方案

### 3.1 并行加载

将当前 `for...await` 改为：

```text
读取 enabled Server
      ↓
Promise.all(每个 Server 的独立加载任务)
      ↓
按原配置顺序合并结果
      ↓
创建 ToolRegistry
```

每个 Server 的加载任务内部仍然保持严格顺序：

```text
spawn
  ↓
initialize
  ↓
notifications/initialized
  ↓
tools/list（包括分页）
  ↓
创建 McpTool
```

并行只发生在不同 Server 之间，不会并行发送同一个 Server 的握手和工具请求。

### 3.2 失败隔离

每个 Server 使用独立的加载函数捕获异常并返回结果对象：

```ts
type McpServerLoadResult = {
  tools: McpTool[]
  client?: McpStdioClient
  diagnostics: string[]
  timings: McpTiming[]
}
```

- 成功：返回 Client 和工具；
- 失败：关闭已经启动的 Client，返回诊断，不抛出到整个 Runtime；
- 关闭失败：保留原始加载错误，同时追加关闭诊断；
- `Promise.all` 只等待所有隔离任务完成，不因单个任务 rejection 提前结束。

### 3.3 稳定排序

`Promise.all` 的结果顺序与输入数组一致，因此工具合并按照配置文件中的 Server 顺序完成，而不是按照哪个子进程先启动完成排序。

工具命名仍然使用：

```text
mcp_<serverName>_<remoteToolName>
```

这样并行加载不会改变已有工具名，也不会引入新的冲突解决规则。

## 4. 耗时诊断

### 4.1 记录阶段

每个启用 Server 记录以下阶段：

| 阶段         | 起止范围                       | 用途                               |
| ------------ | ------------------------------ | ---------------------------------- |
| `spawn`      | 调用 `spawn` 前后              | 判断命令创建是否缓慢或失败         |
| `initialize` | 发送 initialize 到收到响应     | 判断 MCP 握手是否缓慢              |
| `tools/list` | 完成全部分页发现               | 判断工具发现或 Server 扫描是否缓慢 |
| `total`      | 单个 Server 加载任务开始到结束 | 判断该 Server 对启动的完整影响     |
| `mcp-total`  | 所有 MCP 加载开始到结束        | 判断并行后的实际墙钟时间           |

阶段时间使用 `performance.now()`，单位为毫秒并保留两位小数。

### 4.2 输出规则

普通启动不输出额外日志。只有用户传入 `--verbose-startup` 时，才把 MCP 诊断加入启动报告，例如：

```text
PawCode 启动耗时
- config: 4.2ms
- context: 52.1ms
- mcp.demo.spawn: 1.4ms
- mcp.demo.initialize: 38.7ms
- mcp.demo.tools/list: 2.1ms
- mcp.demo.total: 43.0ms
- mcp-total: 44.3ms
- runtime: 47.5ms
- total: 312.4ms
```

由于多个 Server 并行，多个 `mcp.<server>.*` 阶段时间的总和可能大于 `mcp-total`；报告中应明确这些是独立阶段耗时，不直接相加作为墙钟时间。

### 4.3 失败诊断

诊断必须包含 Server 名称和失败阶段能确定的错误，但不能包含完整环境变量、API Key 或其他配置秘密。例如：

```text
配置警告：MCP Server demo 加载失败：MCP initialize 超时（10000ms）
```

失败 Server 的耗时仍然记录，便于判断是快速 spawn 失败还是等待超时。

## 5. 生命周期和资源回收

- 所有 Server 加载任务完成后才创建 AgentRuntime；
- 成功加载的 Client 放入统一 `clients` 数组；
- 失败任务中的 Client 在任务内部关闭，不加入统一数组；
- Runtime 的 `close()` 继续关闭所有成功 Client；
- `/new`、`/resume`、`/branch` 仍然先关闭旧 Runtime，再创建新 Runtime；
- 并行加载不改变已有的进程回收责任。

## 6. 测试计划

### 6.1 自动测试

- 两个延迟不同的 Server 并行加载，总耗时接近较慢 Server，而不是两个耗时相加；
- 一个 Server 失败时，另一个 Server 仍能注册工具；
- 所有 Server 的工具顺序仍按配置顺序；
- spawn、initialize、tools/list 阶段均能产生耗时记录；
- 失败 Server 的子进程被关闭，不残留句柄；
- 默认模式不输出启动耗时，`--verbose-startup` 输出 MCP 阶段耗时。

### 6.2 手动验收

```bash
pnpm dev --verbose-startup --json "请只回复 ok，不要调用工具"
```

检查：

1. 输出中出现 `mcp-` 或 `mcp.` 前缀的阶段；
2. `mcp-total` 接近最慢 Server 的加载时间；
3. 删除或停用一个 Server 后，其他 Server 和内置工具仍可用；
4. 不带 `--verbose-startup` 时不出现耗时明细。

## 7. 验收标准

- 两个可用 MCP Server 的启动等待不再按串行时间累加；
- 单个 Server 超时不会阻断 AgentRuntime 创建；
- `--verbose-startup` 能定位 spawn、initialize、tools/list 和总耗时；
- 现有 MCP、配置、权限和完整测试继续通过；
- 不引入新的凭据输出和子进程泄漏。

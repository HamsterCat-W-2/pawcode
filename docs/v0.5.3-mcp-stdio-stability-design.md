# v0.5.3 MCP stdio 稳定性技术设计

## 1. 文档目的

本文定义 MCP stdio 第一阶段进入稳定使用前需要补齐的错误处理、协议校验和测试边界。

v0.5.2 已解决多个 MCP Server 串行启动导致的启动耗时累加问题。本阶段不改变并行加载方案，重点解决以下问题：

- Server 启动后立即退出时，PawCode 如何诊断和隔离；
- stdout 出现非法 JSON、JSON-RPC 错误或无效响应时，当前请求和当前 Server 分别如何处理；
- initialize、tools/list、tools/call 超时后，哪些 Client 可以继续使用；
- MCP 返回的工具描述和 inputSchema 如何校验；
- 不同 Server 或同一 Server 的工具名称冲突如何阻止进入 ToolRegistry；
- 失败、超时和关闭过程中如何保证没有子进程、计时器和 pending Promise 泄漏。

## 2. 当前实现基线

当前 MCP stdio 流程为：

```text
配置加载
  ↓
并行启动 enabled Server
  ↓
每个 Server：spawn → initialize → notifications/initialized → tools/list
  ↓
合法工具描述映射为 mcp_<server>_<tool>
  ↓
加入 ToolRegistry
  ↓
AgentRuntime 调用
```

已有能力：

- stdio 子进程启动，`shell: false`；
- JSON-RPC request/response ID 匹配；
- initialize、tools/list、tools/call；
- tools/list cursor 分页；
- MCP 工具权限确认；
- MCP Server 并行加载和阶段耗时诊断；
- Runtime 关闭时回收 MCP Client。

本阶段允许调整 MCP Client 内部错误处理和工具描述校验，但不能破坏以下架构边界：

1. MCP 工具必须进入 `ToolRegistry`，不能直接执行；
2. MCP 工具必须经过 `PermissionManager`；
3. MCP Server 必须通过 `spawn(command, args, { shell: false })` 启动；
4. Server 失败只能隔离当前 Server，不能绕过或关闭内置工具；
5. stdout 只能用于 MCP JSON-RPC，诊断信息走 stderr 或 PawCode 的诊断输出；
6. 不把 API Key、环境变量或完整配置写入错误日志。

## 3. 稳定性目标和非目标

### 3.1 目标

- 所有协议异常都转换为稳定、可测试的错误语义；
- 失败 Server 不进入 ToolRegistry，也不留在 Runtime 的 Client 列表中；
- 已成功启动的其他 Server 和内置工具不受影响；
- 失败原因包含 Server 名称、阶段和安全的错误摘要；
- 每个 pending request 都能以成功、失败或超时结束；
- 工具描述无效时给出明确原因，而不是静默丢弃；
- 工具命名冲突在 Runtime 创建阶段被发现并隔离；
- 通过自动测试覆盖进程退出、非法 JSON、JSON-RPC error、超时、分页和关闭。

### 3.2 非目标

- 本阶段不实现 Streamable HTTP；
- 不实现 OAuth、resources、prompts、sampling 或 tasks；
- 不支持运行中自动刷新工具列表；
- 不引入 MCP Server 常驻进程或跨 Session 复用；
- 不允许 MCP Server 自己决定 PawCode 权限；
- 不把所有 MCP 协议字段做成完整通用 JSON-RPC 框架。

## 4. 错误分类

MCP 错误分为四层，不能混用：

| 层级   | 示例                                     | 处理对象                    | 是否关闭 Server                  |
| ------ | ---------------------------------------- | --------------------------- | -------------------------------- |
| 启动层 | command 不存在、spawn 失败               | 当前 Server 加载任务        | 不存在可关闭的有效 Client        |
| 通道层 | stdout 非 JSON、stdin 写入失败、进程退出 | 当前 Client 的 pending 请求 | 是，当前 Server 不再可靠         |
| 协议层 | JSON-RPC `error`、响应缺少 result        | 当前请求或当前阶段          | initialize/tools/list 失败时关闭 |
| 工具层 | MCP `isError: true`、工具参数错误        | 当前工具调用                | 否，Server 可以继续提供其他工具  |

### 4.1 启动失败

`spawn()` 抛出异常时：

- 当前 Server 返回失败诊断；
- 不创建 Client；
- 不创建 MCP Tool；
- 其他 Server 继续加载；
- 内置工具继续可用。

### 4.2 初始化失败

initialize 包括以下校验：

- 请求是否在 `timeoutMs` 内收到响应；
- 响应是否为对象；
- 是否存在可用的 `protocolVersion`、`capabilities` 和 `serverInfo` 结构；
- JSON-RPC error 是否存在。

initialize 失败意味着 Server 尚未建立可用 MCP 会话，因此必须关闭当前 Client，不能继续 tools/list。

### 4.3 tools/list 失败

tools/list 失败包括：

- 请求超时；
- JSON-RPC error；
- result 不是对象；
- cursor 分页返回无效 cursor；
- 某一页无法解析。

tools/list 失败时关闭当前 Client。部分页面已发现的工具也不能注册，避免模型拿到不完整工具列表。

### 4.4 tools/call 失败

tools/call 是运行期操作，与启动阶段不同：

- 请求超时：当前工具返回失败文本，Server 默认保持可用；
- JSON-RPC error：当前工具返回协议错误文本，Server 默认保持可用；
- `isError: true`：转换为工具错误结果，不当作 PawCode 进程崩溃；
- 通道错误或 Server 退出：当前 Client 标记关闭，后续调用立即失败。

如果通道层已经确认不可靠，不能继续向同一 Server 发送新的 tools/call。

## 5. 子进程生命周期

### 5.1 状态模型

每个 `McpStdioClient` 使用以下逻辑状态：

```text
created
  ↓ spawn
started
  ↓ initialize 成功
initialized
  ↓ tools/list 成功
ready
  ↓ close、进程退出或通道错误
closed
```

只有 `ready` Client 才能进入成功结果并向 ToolRegistry 提供工具。

### 5.2 进程提前退出

当 `close` 事件先于当前阶段完成时：

1. 标记 Client 为 closed；
2. reject 所有 pending request；
3. 清理每个 request 的 timer；
4. 当前 Server 返回包含退出 code/signal 的诊断；
5. 其他 Server 和内置工具继续运行。

如果进程已退出，`close()` 必须幂等，不能因为重复 kill 或重复关闭 stdin 导致新的异常覆盖原始诊断。

### 5.3 资源回收要求

每个加载路径都必须满足：

- 成功 Client 由 Runtime `close()` 统一回收；
- 初始化或发现失败的 Client 在当前加载任务中立即回收；
- pending map 在关闭和进程退出后为空；
- timeout timer 在响应、失败、超时和关闭路径都被清理；
- readline interface 和 stdin 在关闭流程中释放。

## 6. JSON-RPC 和 stdout 校验

### 6.1 消息边界

stdio transport 使用逐行 JSON-RPC：

- 空行忽略；
- 每个非空行必须是一个 JSON 对象；
- stdout 中出现普通日志或半行文本视为通道污染；
- 解析失败时，当前 Client 的通道视为不可靠。

不能尝试从混杂日志中提取 JSON，因为这可能把日志中的对象误当成协议响应。

### 6.2 响应匹配

- 有 `id` 的消息才可能完成 pending request；
- 没有 `id` 的消息视为 notification，不完成任何 request；
- 未知 id 的迟到响应忽略，不影响其他 pending request；
- 响应 id 必须能够转换为稳定字符串进行匹配；
- JSON-RPC error 必须转换为包含 code 和 message 的安全错误。

### 6.3 通道错误后的策略

非法 JSON、stdin 写入失败和进程退出都会调用统一的 `failPending()`：

```text
通道错误
  ↓
清理所有 pending timer
  ↓
reject 所有 pending Promise
  ↓
标记 Client closed
  ↓
后续 request 立即失败
```

## 7. 工具描述和 inputSchema 校验

### 7.1 工具名称

MCP 工具必须满足：

- `name` 是非空字符串；
- 转换后的 PawCode 名称不超过模型和 ToolRegistry 可接受长度；
- 不能与内置工具名冲突；
- 不能与其他 MCP Server 生成的完整名称冲突；
- 冲突时当前冲突工具不注册，并输出 Server、原始工具名和最终名称。

完整名称仍按以下规则生成：

```text
mcp_<serverName>_<remoteToolName>
```

### 7.2 描述字段

- `description` 缺失允许使用 PawCode 生成的兜底描述；
- `description` 如果存在必须是字符串；
- 非字符串 description 不应直接传给模型；
- 无效描述不能导致整个 PawCode 进程崩溃。

### 7.3 inputSchema

第一阶段采用最小安全校验：

- 必须是对象；
- `type` 如果存在必须是字符串，推荐为 `object`；
- `properties` 如果存在必须是对象；
- `required` 如果存在必须是字符串数组；
- 不完整或无效 schema 不进入 ToolRegistry；
- 不在 PawCode 内部重新实现完整 JSON Schema validator。

如果 MCP Server 未提供 inputSchema，可以使用默认的宽松 object schema；这与 schema 存在但非法不同，后者必须诊断并跳过。

## 8. 诊断格式

诊断分为用户可读摘要和开发调试细节：

```text
配置警告：MCP Server demo 阶段 tools/list 失败：MCP tools/list 超时（10000ms）
```

要求：

- 包含 Server 名称；
- 尽量包含阶段；
- 包含安全的错误原因；
- 不输出 env、API Key、完整命令中的敏感参数；
- 普通模式只输出失败摘要；
- `--verbose-startup` 可以额外输出阶段耗时；
- JSON 模式中 stdout 继续只输出 NDJSON，诊断走 stderr。

## 9. 测试计划

### 9.1 单元和集成测试

至少增加以下测试：

1. command 不存在时返回诊断，内置路径不被阻断；
2. Server 启动后立即退出时返回退出 code/signal；
3. initialize 超时后 Client 被关闭；
4. tools/list 超时后 Client 被关闭；
5. tools/call 超时返回工具失败结果；
6. Server 输出非法 JSON 时 pending request 被 reject；
7. JSON-RPC error 被转换为安全错误；
8. tools/list 多页 cursor 全部合并；
9. 无效工具名、description 和 inputSchema 不进入 ToolRegistry；
10. MCP 工具与内置工具或其他 Server 冲突时有明确诊断；
11. 一个 Server 失败时其他 Server 仍然成功；
12. 失败和成功路径都没有残留 Client、timer 和 pending request。

### 9.2 验证命令

```bash
./node_modules/.bin/prettier --check .
./node_modules/.bin/tsc --noEmit
./node_modules/.bin/vitest run
./node_modules/.bin/tsc
git diff --check
```

### 9.3 验收标准

- 所有异常测试稳定通过，不依赖人工等待；
- 一个坏 Server 不影响内置工具和其他正常 Server；
- 无效工具不会进入模型工具列表；
- tools/call 的业务错误不会误杀健康 Client；
- 通道错误会阻止后续不安全调用；
- 关闭 Runtime 后没有遗留 MCP 子进程；
- 现有 0.5.1 MCP 调用、权限和启动性能测试继续通过。

## 10. 后续边界

完成本阶段后，再评估：

1. `notifications/tools/list_changed` 动态刷新；
2. Streamable HTTP transport；
3. OAuth 和远程 Server 信任策略；
4. resources、prompts、sampling 和 tasks。

这些能力必须继续复用 `ToolRegistry`、`PermissionManager`、统一诊断和 Runtime 生命周期，不能为远程 MCP 另建一套权限路径。
